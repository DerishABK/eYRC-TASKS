# Task 3A Implementation Plan

**Scope:** Task 3A Mini Theme Run only. Task 3B viva is out of scope.

**Status:** Submission-ready after a successful official Hard run. The final run reached `PARKING->DONE` at frame 1825 with marker-relative forward distance approximately `0.17 m`, and exited normally after 368 seconds of simulation time. The final `NV_Task3_run.csv` was generated by the unchanged final `task3.py`, and `NV_Task3.zip` contains only those two matching files.

## Official requirements

The graded run uses `Task_3_Hard.ttt`. The vehicle must:

1. Follow the road from its spawn point and halt at the Hospital pickup point for **5 seconds of simulation time**, coming fully to rest inside the pickup area.
2. Obey the commanded wheel-speed limits: at most **3.0 rad/s** generally and **1.2 rad/s** from the first Speed 40 sign through the second.
3. Detect obstacles from the camera, change lanes early enough to avoid obstacles in its current lane, and remain in the new lane after passing them.
4. Complete the route and park in the ArUco parking bay, stationary inside the parking area, after passing the obstacles.

The program may use the vehicle camera and the provided image-processing libraries. It must not read vehicle, sign, or obstacle positions from the simulator, move the vehicle directly, change the scene, or start/stop the simulation. The evaluator controls the run.

## Submission constraints

- The only solution file is `task3/task3.py`; all custom Python code must be in that file. It must not import project code from `task1*`, `task2*`, or another local Python file.
- Keep Task 2 reference images in the folder for local development if useful, but do not include them in the submission ZIP.
- A graded run must be made with the exact final `task3.py`; changing even a comment after recording requires a new run.
- The final ZIP is exactly `NV_Task3.zip`, containing only `task3.py` and the evaluator-produced `NV_Task3_run.csv`. The separate screen recording must show that same run.

## Proposed single-file architecture

`task3.py` will contain the vision, control, state machine, simulator connection, and main loop in one self-contained file. The main loop will read one camera frame per control cycle and pass observations to a finite-state mission controller.

### 1. Camera perception

- Normalize the sensor buffer to an upright BGR image, following the provided Task 2 camera-reading convention.
- Fit the yellow road edge and dashed divider, and retain stable lane-boundary tracks through bends and short marking gaps. Return both lane geometry and confidence so the controller can hold the selected lane or slow/stop safely when vision is uncertain.
- Detect the four allowed sign classes (`Hospital`, `School`, `Speed40`, `Parking`) from image appearance using the supplied Task 2B sample/reference images as development data. Include apparent size and image position in the internal detection result so the controller can decide approach and relevance from the live image.
- Detect red obstacles in the image, separate them from red sign regions, estimate their apparent size and image position, and decide whether each obstacle lies in the currently targeted lane.
- Detect the target ArUco marker using the Task 2C camera method and estimate the parking-relative pose from its image corners only.

### 2. Mission state machine

Use explicit states and one-way event transitions rather than elapsed-time or arena-coordinate triggers:

1. **FOLLOW_TO_HOSPITAL** — lane-follow; ignore School for stopping; begin braking when the Hospital sign is visually close enough to reach the pickup patch safely.
2. **HOSPITAL_STOP** — command zero drive speed; begin the five-second timer only after the vehicle is actually at rest; measure elapsed time with `sim.getSimulationTime()`; mark the Hospital stop complete before moving again so the same sign cannot retrigger it.
3. **FOLLOW_AND_OBEY_SPEED_SIGNS** — retain speed-zone state after the first Speed 40 sign leaves view; restore normal speed only after the second Speed 40 sign. Clamp every commanded speed to the applicable limit, with lower speeds allowed for curves, recovery, and parking.
4. **AVOID_OBSTACLE / LANE_CHANGE** — react only to an obstacle classified in the target lane. Start early using its image size and lane-relative position; steer toward the adjacent lane center with the lane controller; latch the new lane target once acquired and do not return to the previous lane just because that obstacle disappears. Reassess later obstacles from the camera.
5. **APPROACH_PARKING** — ignore Parking signs until the Hospital stop is complete and obstacle-passing requirements are satisfied. Approach only when the Parking cue and visible ArUco marker support a safe handoff to the parking controller.
6. **PARKING** — use the Task 2C marker-relative lateral, heading, and forward estimates to enter the bay, align, stop within it, and report completion.
7. **DONE / SIMULATION_ENDED** — hold both drive motors at zero after parking; exit cleanly when the evaluator stops the simulation.

The state machine will record event flags (Hospital stopped, speed-zone sign count/state, lane target, obstacles detected/passed, parking committed) to prevent repeated sign triggers and premature parking. It will not use simulator object positions, fixed turn delays, or hard-coded obstacle coordinates.

### 3. Control and safety behavior

- Reuse the proven Task 2A lane-centering and Ackermann steering approach, adapting it so the target can be either lane during an intentional lane change.
- Reduce speed for tight curvature, lane changes, uncertain line fits, and parking. Never exceed the current sign-controlled speed cap.
- When a sign or obstacle detector is temporarily uncertain, preserve the last valid lane estimate briefly while reducing speed; do not make a sudden lane switch based on a single weak frame.
- Apply steering and speed through the supplied joint handles only. Do not call `sim.setObjectPosition()` or `sim.setObjectOrientation()`.
- Keep the loop active during the Hospital halt and wait using simulation time, not `time.sleep()` as a timer.

## Implementation sequence after plan approval

1. Create the self-contained `task3/task3.py` skeleton, imports, scene handles, camera reader, Ackermann mapping, and lifecycle loop.
2. Inline and adapt Task 2A lane perception/control; add explicit current-lane and target-lane tracking.
3. Implement sign and obstacle perception from Task 2B examples, then connect Hospital stop, Speed 40 zone, and obstacle-triggered lane-change states.
4. Inline Task 2C marker pose estimation, implement the parking controller, and gate parking on mission progress.
5. Walk through behavior in Easy, then Medium, then Hard; tune perception thresholds and control constants against actual camera frames and verify each state transition.
6. Run the full Hard evaluator repeatedly. Inspect evaluator output, generated CSV, simulation behavior, speed/stop/parking feedback, and script/recording consistency. Only package after a successful final graded run.

## Acceptance checklist

- One `task3.py`, with no imports from other project Python files.
- Easy: lane following, Hospital stop, Speed 40 behavior, and parking path work without obstacles.
- Medium and Hard: an obstacle in the target lane triggers an early lane change; a clear neighboring lane is acquired; the car avoids contact and does not revert after the obstacle passes.
- Hard graded run: Hospital stop is fully stationary for at least five simulation seconds in the pickup patch; speed caps are never exceeded; obstacles are passed without collision; no wheel leaves the road; the vehicle parks and stops within the bay.
- Script exits when the evaluator ends the simulation and has no blocking GUI or input calls.
- Final evaluator CSV and ZIP correspond byte-for-byte to the final script; ZIP contains only the two required files.
- Separate unlisted video is continuous and shows the same Hard run, full CoppeliaSim window with simulation time, and evaluator terminal output.

## Known tuning risk to resolve during implementation

The local Task 2B and Task 2C controllers are placeholders, and Task 3 asks for a camera-estimated Hospital pickup stop distance and reliable lane-change commitment around obstacles. These need to be calibrated in the supplied scenes rather than filled with fixed arena coordinates or elapsed-time guesses. The plan is to validate them incrementally in Easy/Medium before attempting repeated Hard runs.
